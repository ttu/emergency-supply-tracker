# Days Covered — make the KPI mean what it says

**Status:** Implemented
**Date:** 2026-08-04
**Affects:** v2 Dashboard KPI row (`DAYS COVERED`)

---

## 1. Problem

The `DAYS COVERED` tile on the v2 dashboard does not measure days. It measures the
share of inventory rows whose status is `ok`, rescaled onto the day axis.

`src/shared/hooks/useDesignData.ts:88-91`:

```ts
const okRatio = totals.total > 0 ? totals.ok / totals.total : 0;
const daysCovered = household.supplyDurationDays
  ? Math.round(okRatio * household.supplyDurationDays * 10) / 10
  : 0;
```

Three consequences:

1. **It is a lie by unit.** No liter, kcal, person, or consumption rate enters the
   formula. A household with 10× the required water and one expired flashlight
   scores the same as one with barely enough water.
2. **It is redundant.** `readiness` on the same hook is `okRatio * 100`
   (`src/shared/utils/designStatus.ts:70-79`). The two tiles show one number in two
   costumes.
3. **It contradicts the rest of the app.** A user with water at `70 / 64 L` (OK) and
   food at `66355 / 21000 kcal` (OK) is shown `2.8 / 7 days`. Both statements are
   generated by this codebase; only one can be true.

Reported by the user from live data: 58 items, 23 `ok`, both survival categories over
target, KPI reads 2.8.

## 2. Goal

`DAYS COVERED` answers one question: **for how many days can this household drink and
eat from what is stocked?** Everything else — expiring flashlights, missing duct
tape — is already covered by the Readiness, Expiring and Critical tiles and must not
enter this number.

Non-goal: replacing Readiness. The two tiles become genuinely different measurements,
which is the point.

## 3. Model

Two survival resources have a defensible per-day burn rate. Nothing else in the
inventory does.

### 3.1 Food

```
calorieRatePerDay = totalNeededCalories / supplyDurationDays
foodDays          = totalActualCalories / calorieRatePerDay
```

`totalNeededCalories` is already `dailyCalories × peopleMultiplier ×
supplyDurationDays` (`strategies/food.ts:86-91`), so dividing it back out recovers the
daily rate **including** the user's Nutrition Settings override and the
adult/child multipliers. No new constants, no duplicated household maths.

### 3.2 Water

Water has a fixed overhead: preparing stored food consumes liters
(`strategies/water.ts:87-108` exposes `drinkingWaterNeeded` and
`preparationWaterNeeded`). Preparation water does **not** scale with days — it scales
with how much food is on the shelf.

Charging the whole preparation reserve against day 1 would mean _buying more food
lowers your water days_, which is absurd. Instead amortize it over the food it
prepares:

```
drinkingRatePerDay = drinkingWaterNeeded / supplyDurationDays
prepRatePerDay     = preparationWaterNeeded / foodDays      // foodDays > 0
waterDays          = totalActual / (drinkingRatePerDay + prepRatePerDay)
```

Each day you drink your ration and cook one day's worth of food. Self-consistent, and
non-recursive because `foodDays` is computed first.

### 3.3 Result

```
daysCovered = min(foodDays, waterDays)
```

Rounded to one decimal, **not** capped at the target. Capping would hide that a user
has 22 days of food, and the tile's own subtitle already states the target so
`14.1` against `TARGET: 7D` reads correctly as "ahead of goal".

### 3.4 Worked example (the reported data)

| Input                                         | Value              |
| --------------------------------------------- | ------------------ |
| `totalActualCalories` / `totalNeededCalories` | 66355 / 21000 kcal |
| `supplyDurationDays`                          | 7                  |
| water `totalActual`                           | 70 L               |
| `drinkingWaterNeeded`                         | 21 L               |
| `preparationWaterNeeded`                      | 43 L               |

```
calorieRate = 21000 / 7 = 3000 kcal/day
foodDays    = 66355 / 3000 = 22.1
drinkRate   = 21 / 7 = 3.0 L/day
prepRate    = 43 / 22.118 = 1.944 L/day
waterDays   = 70 / 4.944 = 14.2
daysCovered = min(22.1, 14.2) = 14.2
```

Tile shows **14.2**, target 7 — consistent with both category panels showing OK.

## 4. Edge cases

| Condition                                                      | Behaviour                                                                                 |
| -------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `supplyDurationDays` is 0 / undefined                          | return 0                                                                                  |
| Food category disabled or absent from `categoryStatuses`       | `foodDays = undefined`; result is `waterDays` alone                                       |
| Water category disabled or absent                              | `waterDays = undefined`; result is `foodDays` alone                                       |
| Both absent                                                    | return 0                                                                                  |
| `totalNeededCalories === 0` (no recommendations, "none" kit)   | `foodDays = undefined` — no rate, no claim                                                |
| `drinkingWaterNeeded === 0` and `preparationWaterNeeded === 0` | `waterDays = undefined`                                                                   |
| `foodDays === 0` (no calories stocked)                         | short-circuit to 0; skip the `prepRate` division                                          |
| Water `primaryUnit !== 'liters'`                               | `waterDays = undefined` — `totalActual` is a mixed-unit sum and dimensionally meaningless |
| Result non-finite (NaN/Infinity from bad stored data)          | return 0                                                                                  |
| Result > 999                                                   | clamp to 999 so the tile cannot break its layout                                          |

Rounding happens **once**, at the end: `Math.round(x * 10) / 10`.

## 5. Implementation

### 5.1 New pure module

`src/shared/utils/calculations/daysCovered.ts`

```ts
export interface DaysCoveredResult {
  /** min(foodDays, waterDays), rounded to 1dp; 0 when nothing is measurable. */
  days: number;
  /** Days of calories on hand; undefined when food is not measurable. */
  foodDays?: number;
  /** Days of drinking + preparation water; undefined when not measurable. */
  waterDays?: number;
  /** Which resource is the binding constraint — drives the tile's detail line. */
  limitedBy?: 'food' | 'water';
}

export function calculateDaysCovered(
  categoryStatuses: CategoryStatusSummary[],
  supplyDurationDays: number,
): DaysCoveredResult;
```

Pure, no hooks, no React. `CategoryStatusSummary` already carries every input
(`totalActualCalories`, `totalNeededCalories`, `totalActual`, `primaryUnit`,
`drinkingWaterNeeded`, `preparationWaterNeeded`), so this module owns arithmetic only.

Category lookup uses the existing predicates: `isFoodCategory(id)` from
`@/shared/types` and the `'water-beverages'` id (mirror the constant already used in
`CategorySummaryPanel.tsx:9`; promote it to `constants.ts` as
`WATER_CATEGORY_ID` and import it in both places rather than duplicating a third
literal).

### 5.2 Wiring

`src/shared/hooks/useDesignData.ts`

- Delete the `okRatio`-based `daysCovered` block (lines 88-91).
- Call `useCategoryStatuses()` (`@/features/dashboard`) and pass
  `categoryStatuses` + `household.supplyDurationDays` into `calculateDaysCovered`.
- Widen `DesignData`: keep `daysCovered: number` for existing consumers, add
  `daysCoveredDetail: DaysCoveredResult`.

`useCategoryStatuses` is already memoized and already mounted on the dashboard via
`CategorySummaryPanel`, so this adds no meaningful render cost. Watch for an import
cycle: `useDesignData` lives in `shared/`; if importing `@/features/dashboard` from
`shared/` trips the lint boundary rule, take `categoryStatuses` as an argument to
`useDesignData` from the dashboard instead of importing it — decide when the ESLint
run says so, do not pre-emptively restructure.

### 5.3 UI

`src/features/dashboard/components/v2/KpiRow.tsx`

- Value: `daysCoveredDetail.days.toFixed(1)` (unchanged shape).
- Add a tone, matching the tile's siblings which all carry one:
  `days >= supplyDurationDays → 'ok'`, `>= supplyDurationDays * 0.6 → 'warn'`,
  else `'crit'`.
- Replace the detail line with a limiting-factor line when
  `limitedBy` is set, e.g. `LIMITED BY: WATER` — that is the actionable half of the
  number and currently nowhere in the UI.

**Bug found while specifying, fix in the same change:** `v2.dashboard.kpiTarget` is the
hardcoded string `"TARGET: 7D"` / `"TAVOITE: 7VRK"` (`common.json:1088-1092`). A
household configured for 3 days is shown a 7-day target. Convert to interpolation:
`"TARGET: {{days}}D"` / `"Goal: {{days}} days"` / `"TAVOITE: {{days}}VRK"` and pass
`household.supplyDurationDays`, in all three voices, EN and FI.

New keys (EN + FI, all three voices: `cockpit`, `civil`, `pantry`):

- `v2.dashboard.kpiLimitedBy` — `"LIMITED BY: {{resource}}"` / `"Limited by {{resource}}"`
- `v2.dashboard.limitFood`, `v2.dashboard.limitWater` — resource names

Run `npm run validate:i18n` after.

## 6. Tests (TDD — these get written first)

`src/shared/utils/calculations/daysCovered.test.ts`, pure fixtures built from
`CategoryStatusSummary` literals:

1. Food-only inventory → `days === foodDays`, `limitedBy === 'food'`.
2. Water-only inventory → `days === waterDays`, `limitedBy === 'water'`.
3. Both present, water lower → returns water, `limitedBy === 'water'`.
4. Both present, food lower → returns food, `limitedBy === 'food'`.
5. **The reported scenario** (§3.4 numbers) → `14.1`. This is the regression test; it
   fails against today's code, which returns `2.8`.
6. Zero preparation water → `waterDays === totalActual / drinkingRate` exactly.
7. Preparation water present → water days strictly lower than in case 6, and adding
   _more_ food (higher `totalActualCalories`, same `preparationWaterNeeded`) does not
   reduce `waterDays`. Guards the amortization decision in §3.2.
8. `supplyDurationDays === 0` → `0`.
9. Each disabled/absent-category row from the §4 table → asserted individually.
10. `totalActualCalories === 0` → `0`, and no NaN in `foodDays`/`waterDays`.
11. Mixed-unit water (`primaryUnit === 'pieces'`) → `waterDays === undefined`.
12. Rounding: a value of `7.049` → `7.0`; `7.05` → `7.1`.

`KpiRow.test.tsx`: renders the value from `daysCoveredDetail`, renders the limiting
line, renders the interpolated target for a 3-day household (asserts the hardcoded-7
bug is gone), and applies the crit tone below 60% of target.

E2E: extend the existing v2 dashboard spec — seed a household plus known water and
food items via localStorage, assert the tile reads the expected days rather than a
readiness echo. Per `docs/TESTING_STRATEGY.md` the weight sits on the unit tests here;
this is one confidence check, not a matrix.

Coverage target for `daysCovered.ts`: 100% branch (it is pure business logic —
`AGENTS.md` §Business logic).

## 8. Risks

- **Numbers move a lot.** The reported household goes 2.8 → 14.1. That is the fix
  working, but any visual-regression baseline containing the KPI row needs updating
  (`npm run test:e2e:visual:update`).
- **Food days depend on calorie data being present.** Items lacking
  `caloriesPerUnit` contribute 0 kcal, understating `foodDays`. This is pre-existing —
  the same figure already drives the Food category panel — so it is not made worse
  here, but it is the most likely source of a "this still looks wrong" follow-up.
- **Water `totalActual` counts all beverages in the category** (juice, long-life milk),
  not just potable water; `calculateTotalWaterAvailable` in `calculations/water.ts` is
  stricter. Using `totalActual` is deliberate: the KPI must agree with the `70 / 64
liters` the inventory panel prints one click away, and diverging would trade one
  credibility bug for another. Worth a separate issue to align both on a single
  definition.

## 9. Out of scope

Changing category status rules, the Readiness formula, `calculateItemStatus`, or the
`primaryUnit` mixed-unit aggregation. Those are load-bearing for v1 and v2 alike and
have their own extensive test suites.
